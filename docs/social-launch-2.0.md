## 一、小红书首发

### 标题备选

1. 我和 AI 把一个翻译 App 的 UI 重做了五遍
2. GemmaTrans 2.0：这次终于把液态玻璃做对了

推荐使用第 1 个标题。它比单纯宣布版本更新更有故事，也更容易让非开发者理解这次 2.0 的投入。

### 正文

GemmaTrans 2.0 终于完成了。

它是一个完全运行在 Mac 本地的 AI 划词翻译工具：选中文字按下快捷键，译文就会出现在浮窗里。模型下载完成后，翻译内容不会离开你的电脑，也没有订阅。

但这次 2.0，我花时间最多的并不是再塞几个功能，而是和 AI 一起把整个 UI 和交互重新做了一遍。

最开始的想法很简单：既然是新的 macOS，就做一套 Liquid Glass。

第一版确实很“玻璃”，也很容易让人觉得好看。但真正用起来，很快就能发现问题：

- 窗口、卡片和按钮都在发光，反而没有重点；
- 浅色模式灰蒙蒙，深色模式的蓝色又太重；
- 同一组按钮大小不一，状态还会在蓝、黄、绿之间跳；
- 翻译长文时浮窗会变得很大，原文和操作甚至会被挤掉；
- 快捷翻译偶尔还会把主窗口一起带到最前面。

这些都不是“再调一个颜色”就能解决的问题。

于是我们不再让 AI 凭一句“做得高级一点”自由发挥，而是开始了一套更像真实设计协作的流程：

1. 先把主窗口、设置页、模型行、翻译浮窗拆成组件；
2. 用设计审查 Skill 逐项找出信息层级、假入口、密度和交互问题；
3. 每次修改都写清楚 Before / After / Why；
4. 把颜色、间距、圆角、材质、按钮状态和动效规则写进项目自己的 `DESIGN.md`；
5. 每一轮都启动 fresh build，重新截浅色、深色和长文本状态；
6. 真实使用不对，就推翻上一版，而不是继续往上叠样式。

过程中我们也走过弯路。

有一版为了让结果更突出，把原文默认折叠了。设计逻辑听起来很合理，但实际看起来没有之前漂亮，对照翻译也不方便。最后我们重新回到真实使用场景，继续调整浮窗结构。

还有光标和占位文字差几像素、复制和朗读按钮尺寸不一致、菜单栏点“设置”却没有把窗口带到前台……这些看起来都是很小的细节，但一个工具是否精致，往往就藏在这些地方。

最后形成的 GemmaTrans 2.0，不是“玻璃越多越好”，而是让玻璃只负责表达空间和操作层级：

- 内容保持安静，译文永远是主角；
- 主窗口、设置和浮窗使用同一套设计语言；
- 浅色与深色都保持清楚的文字对比；
- 翻译浮窗可以固定位置，适合逐段翻译长文；
- 四款本地模型由用户自己选择，不会首次启动就偷偷下载；
- Hugging Face 不可用时会自动切换国内下载源；
- 本地 API 可以接 PopClip、Bob、Raycast 等工具。

这次最有价值的收获，不是找到了一个“一句话生成好 UI”的 Prompt。

而是我们终于找到了一种和 AI 一起做设计的方式：给它设计上下文、让它接受审查、用真实截图验证，再由人决定什么时候应该推翻 AI。

## 三、V2EX 技术帖

### 节点建议

### 标题

[分享创造] GemmaTrans 2.0：我和 AI 重构了五轮 macOS UI，最后把设计规则写进了仓库

### 正文

大家好，我最近完成了 GemmaTrans 2.0。

项目地址：
https://github.com/Rand01ph/gemma-trans

2.0 下载：
https://github.com/Rand01ph/gemma-trans/releases/tag/v2.0.0

GemmaTrans 是一个运行在 Apple Silicon Mac 上的本地翻译工具，底层基于 MLX-Swift，支持 Google Gemma 4 和腾讯混元 Hy-MT2。模型下载完成后，翻译在本机完成；没有云端 AI 请求，也没有订阅。

它支持三种使用方式：

1. 主窗口输入或粘贴；
2. 在任意 App 选中文字，通过 macOS Service 快捷键翻译；
3. 复制文字后按全局快捷键，在浮窗中查看结果。

这次 2.0 除了模型选择、自动下载源回退、本地 API 和长文翻译浮窗，投入最多的是一次完整的 SwiftUI UI 与交互重构。

#### 一开始，我们以为问题只是“把 Liquid Glass 做好看”

前几版从代码上看都没有太大问题：用了原生 `glassEffect`，主窗口、卡片、浮窗和按钮也有了新的视觉效果。

但实际运行以后，问题很明显：

- 多层玻璃互相竞争，内容和容器没有层级；
- 浅色模式带灰蓝和黑色叠层，正文对比不够；
- 深色模式的大面积高饱和蓝很容易产生色度振动；
- 模型行里的“下载 / 使用 / 当前使用”占位不稳定；
- 翻译浮窗在长文本和流式输出时尺寸变化过于频繁；
- 一些看起来可点击的图标并没有真实功能；
- 快捷翻译与菜单栏窗口命令混用了置顶逻辑。

这些并不是继续调几个 RGB 值就能解决的。它们涉及信息架构、affordance、状态模型和窗口行为。

#### 后来我们改变了和 AI 协作的方式

之前的循环大致是：

> 描述“更高级 / 更有科技感” → AI 改代码 → 编译通过 → 看起来还行

后来变成了：

> 组件审计 → 设计原则 → Before / After / Why → 实现 → fresh build → 浅色/深色截图和真实交互 → 纠偏

我们使用设计审查 Skill 找问题，但不把 Skill 的结论当成不可推翻的答案。

其中有一版为了强调译文，把原文默认折叠。这个推导符合“结果优先、减少噪音”的原则，但实际使用后，我们发现它削弱了对照关系，视觉上也没有之前自然。最终还是根据真实使用感受推翻了方案。

这件事对我启发很大：设计原则是讨论选择的语言，不是替用户做决定的答案生成器。

#### `DESIGN.md` 成了人和 AI 共用的设计合同

项目根目录现在有一份 `DESIGN.md`。它不只记录色值和圆角，还规定了：

- 内容、窗口外壳和操作控件分别使用什么材质；
- Accent、就绪、失败、危险操作分别如何表达；
- 设置行、模型状态槽和短字段的固定尺寸；
- 流式输出何时允许调整窗口大小；
- 浅色、深色、增强对比度和降低透明度如何验收；
- 哪些未完成能力不能提前出现在 UI；
- 每次视觉修改需要覆盖哪些截图和交互场景。

例如最后形成的一条核心规则是：

> 内容不是玻璃。玻璃主要负责表达窗口层级和操作；译文阅读面保持安静。

这份文档进入 Git 之后，后续无论是我还是新的 coding agent，都不用重新猜“这个项目到底想要什么风格”。

#### 设计验收也需要可靠的工具链

我们还在项目里固定了 fresh build 流程：

- 停止正在运行的旧版本；
- 用 XcodeGen 重新生成项目；
- 构建当前 worktree；
- 从生成产物的绝对路径启动；
- 校验实际进程、Bundle ID 和本地 API 端口归属。

听起来和 UI 没关系，但它解决了一个很现实的问题：如果截图来自 `/Applications` 里的旧 App，后面所有设计判断都会建立在错误证据上。

因此现在的“UI 完成”有两层含义：

1. Swift 代码编译通过；
2. 正确构建在真实尺寸、状态和操作路径里成立。

#### 2.0 最终落地的内容

- 原生 Liquid Glass 主窗口、三标签设置页和结果优先翻译浮窗；
- 浅色、深色及系统 Accent 的统一语义；
- 可固定位置的翻译浮窗，适合逐段翻译长文；
- 四款本地模型按需下载，首次启动不再自动联网；
- Hugging Face 不可用时自动回退 ModelScope；
- 本地 `/translate` 与兼容 `/v1/chat/completions` 请求格式的 HTTP API；
- 修复新版 Gemma 4 checkpoint、长文本显示、连续请求覆盖和窗口置顶等问题。

技术栈主要是 SwiftUI、AppKit 窗口桥接、MLX-Swift、XcodeGen。2.0 需要 Apple Silicon Mac 和 macOS 26 或更高版本。

这次最大的收获不是某个 Liquid Glass API，而是把“审美”变成了一个可以审查、实现、验证和回滚的工程过程。

如果大家愿意试用，很欢迎反馈两类问题：

1. 翻译质量和不同模型在你机器上的速度；
2. 浅色/深色模式、长文本浮窗和连续翻译的交互感受。

也欢迎对 `DESIGN.md` 或这种 AI 协作方式提建议。
