# 通用开发与发布策略

版本：1.0。状态：已确认的目标策略。项目的具体工具、标识和迁移进度由配套项目说明记录。

本文可复制到其他项目，并由其根目录 `AGENTS.md` 显式引用。复用时应建立该项目自己的配置文件，不能照搬应用 ID、签名团队、检查名称或历史验收结果。策略修改通过 PR 审阅。

## 1. 分支模型

| 分支 | 来源与职责 | 去向 |
| --- | --- | --- |
| `main` | 稳定发布主线；正式构建唯一来源 | 修复同步到 `develop` |
| `develop` | 下一版本的开发集成；不直接正式发布 | 发布冻结后进入 `release/*` |
| `codex/<topic>` | 通常从 `develop` 创建，完成单一功能或修复 | PR 到 `develop` |
| `release/X.Y.Z` | 从选定开发提交创建；只收版本调整和本次发布必要修复 | PR 到 `main`，修复同步回 `develop` |
| `hotfix/<topic>` | 从实际线上版本的不可变 tag 创建 | PR 到 `main`，再同步回 `develop` |

默认使用 `codex/` 前缀创建普通工作分支；上述 `release/`、`hotfix/` 是约定的专用前缀。短期分支完成合并与同步后才能清理，不删除有未提交工作或尚未交付内容的分支。`main` 不提前接纳尚未准备发布的下一版本功能。

功能 PR 可 squash。发布分支进入 `main` 时保留清晰的合并记录，避免长期分支间反复 squash 造成祖先关系混乱。合并产生的新 `main` SHA 必须经过正式构建验证；不能沿用合并前分支 SHA 的产物作为它的发布包。

若 `main` 已含未上线内容，而旧版本需要紧急修复：先明确本次发布范围和冻结顺序，隔离未发布内容，通过可审阅 PR 调整主线；不得把带有额外功能的主线误当作线上基线，也不得强推回退历史。

## 2. PR 与分支保护

- `main`、`develop` 的修改通过 PR；禁止强推、删除共享主线或绕过必需检查。
- PR 描述说明具体问题、结果、验证和未完成项；以当前最终改动为准。
- 最新候选提交必须通过项目规定的 Xcode Cloud 检查；旧 SHA 的通过结果不替代新提交。
- 若平台采用合并候选检查或合并队列，确认构建对应正确候选，不能只检查过期分支头。
- 配置必需检查时使用实际回传的稳定名称，不能写一个从未执行的检查名称。
- 评审与合并权限由项目配置确定；失败检查不能靠重命名、删除或标记成功绕过。

## 3. 流水线职责

| 流程 | 触发 | 工作 | 发布行为 |
| --- | --- | --- | --- |
| PR 验证 | PR 创建或更新 | 配置/契约检查、相关测试、编译验证 | 不上传正式版本 |
| 集成验证 | `develop` 更新 | 集成测试、编译；按需内部测试产物 | 不正式发布 |
| 正式发布 | 手动选择 `main` 上的确定提交 | 发布前检查、测试、Release 归档、签名、上传 | 上传后等待平台处理与验收 |

远端编译、测试、归档、签名统一由 Xcode Cloud 执行。GitHub 保存代码、PR、tag、发布说明并展示回传状态；若保留 Actions，只允许无需编译的仓库管理或发布已验收产物的任务。普通检查脚本也由 Cloud 调用，避免维护重复的实现。

本地开发构建、真实模型验证、固定环境的截图验收允许继续运行，必须标记用途；它们不能取代正式发布产物，也不另建第二条远端发布构建流水线。云端无法稳定复现的 UI 检查由专用图形会话完成并记录环境、源 SHA、结果。

## 4. 发布与 tag

1. 确认当前线上 tag、远端分支、版本与 build。先检查工作区；网络失败时明确标记未刷新，不把缓存当最新事实。
2. 在发布/修复分支完成版本调整、文案、必要验收，通过 PR 合入 `main`。
3. 选择确定的 `main` 提交，触发一次正式构建。记录实际检出的 SHA、工具链和签名身份。
4. 完成上传、平台处理、安装和关键路径验收，关联该构建并提交审核。各阶段单独报告。
5. 审核通过、准备上线时，对该产物对应的源 SHA 创建带说明的正式 `vX.Y.Z` tag。核对它属于 `main`，并与产品版本一致。
6. 使用同一个已验收构建发布，发布说明绑定同一 tag，核实实际可用状态。
7. 同步修复到 `develop`，完成记录后清理短期分支。

正式 tag 不移动、不覆盖、不复用。候选可使用 `vX.Y.Z-rc.N`，它不表示已上线。tag 创建不触发再次编译；源 SHA、产物及 build 不应因打 tag 改变。审核要求改代码时，先更新版本/build、重新合入 main 和构建；不能把新产物挂在旧源提交上。

不同合并操作会产生不同 SHA。发布记录应明确：tag、源 SHA、营销版本、build、Cloud run、产物标识/可用校验值、审核与上线状态。Cloud 的流水线序号与 App 的 build 号可能不同，必须分别记录。

保持发布阶段 main 范围可控；新发布尚未完成时，不随意混入下一版本。发布已发生后的回滚以恢复服务或新补丁为准，遵守平台能力，不能通过移动 tag 假装旧包变成了新包。

## 5. UI、隔离与凭证

- 无明确 UI 调整要求时维持界面契约；故意变化需说明原因、更新契约并审阅基线，禁止自动接受新截图。
- 固定截图环境不匹配时报告无法验收；不得屏蔽整个文字/按钮区域来消除差异。
- 开发、QA、UI 测试与正式安装隔离身份、设置和数据，禁止通过覆盖生产安装来方便测试。
- 密钥由授权的凭证管理系统在运行时提供；仓库只保存引用或非秘密配置。认证成功不等于分发签名、上传或审核成功。
- 发布说明仅包含本次已交付行为，不泄露尚未公开的功能或开发计划。

## 6. 迁移旧流程

先盘点实际分支、触发条件、必需检查、签名路径与未完成构建；再建立替代流程并在真实 PR 上验证。确认回传、日志、失败阻断都有效后，切换必需检查并移除重复构建。打正式 tag 前必须停用旧的 tag 构建触发器。

保存现有开发进度，使用普通提交/PR 调整主线，不重写共享历史。若从 main 撤回过功能，未来重新引入必须显式恢复；不能假设 merge 会自动恢复已 revert 的内容。

文档落地、流水线迁移、保护规则生效、发布完成是四个不同状态，应在项目说明中分别记录。
